# Admin Fulfillment Shipping Browser Smoke Coverage

## Task Classification

Complex Task.

This is a frontend-focused browser smoke coverage task for a high-risk admin order lifecycle write path. The smoke must exercise the real Vue admin order UI in Chromium, intercept gateway API calls hermetically, and verify fulfillment shipping behavior across authorization, request payload, status boundaries, duplicate-submit protection, error envelope rendering, and list/detail synchronization.

This planning round is Codex-only for PRD, research, Trellis context, and handoff. Codex must not modify business implementation files in this round.

## Goal

Define and hand off implementation of real Chromium smoke coverage for:

```text
POST /api/admin/fulfillments/{orderId}/ship
```

The smoke coverage must prove that an authorized ops/admin user can ship a paid unshipped order, cannot ship orders in invalid lifecycle states, sends the expected gateway request with ops auth and a client `requestId`, trims `carrier` and `trackingNo`, guards duplicate submit while pending, preserves backend error envelopes, and synchronizes the admin order detail/list view after success without corrupting the order main status with payment state.

## Scope

In scope:

- Extend or reuse the existing admin order/payment Playwright smoke suite and fixture structure.
- Add hermetic browser route mocks for fulfillment shipping success and failure.
- Cover paid unshipped, created, shipped, completed, cancelled, and unknown-status orders.
- Verify route, method, authorization header, request payload, pending duplicate-submit behavior, error UI, and post-success detail/list synchronization.
- Reuse existing gateway envelope and frontend DTO types where available.
- Keep all browser tests independent of live backend, DB, Redis, MQ, Nacos, logistics provider, or payment service.

Out of scope:

- Backend Java service changes.
- Database migrations or schema changes.
- Gateway route/security config changes.
- Redis, MQ, Nacos, Docker, CI, or infra changes.
- New fulfillment API contract design beyond asserting the existing frontend contract.
- Broad refactors of admin order, payment, product, review, seckill, or mall order code.
- New dependencies or package-manager metadata changes. No new dependency is expected.

## API Contract Under Test

Route:

```text
POST /api/admin/fulfillments/{orderId}/ship
```

Auth:

```text
Authorization: Bearer <ops access token>
```

Expected auth context:

```text
ops/admin session with order-management fulfillment permission
```

Expected request payload:

```json
{
  "requestId": "generated-client-request-id",
  "carrier": "SF Express",
  "trackingNo": "SF123456789CN"
}
```

Payload expectations:

- `requestId` is a non-empty string generated by the client-side flow.
- `carrier` is trimmed before submit.
- `trackingNo` is trimmed before submit.
- Empty or whitespace-only carrier/tracking input must not send a ship request if the current UI validation already blocks it.
- The smoke should assert the observed existing contract. If field names differ in current code, DeepSeek must update this PRD note in the task context before implementing tests.

Expected success envelope shape:

```json
{
  "code": "ADMIN_FULFILLMENT_SHIPPED",
  "message": "OK",
  "data": {
    "orderId": 1002,
    "orderNo": "ADM-PAID-1002",
    "status": "shipped",
    "fulfillmentStatus": "shipped",
    "carrier": "SF Express",
    "trackingNo": "SF123456789CN",
    "traceId": "trace-admin-ship-success"
  },
  "traceId": "trace-admin-ship-success",
  "timestamp": "2026-05-16T08:00:00+08:00"
}
```

Expected failure envelope shape:

```json
{
  "code": "ORDER_STATUS_INVALID",
  "message": "Only paid unshipped orders can be shipped.",
  "data": null,
  "traceId": "trace-admin-ship-invalid",
  "timestamp": "2026-05-16T08:00:00+08:00"
}
```

## Validation And Error Matrix

| Case | Mock HTTP | Code | Required UI / Test Behavior |
| --- | --- | --- | --- |
| Missing ops session | N/A | N/A | Admin order workspace remains protected; no fulfillment ship API call is made. Existing smoke may already cover session bootstrap. |
| Unauthorized ops role | N/A | N/A | Shipping action is unavailable and no fulfillment ship API call is possible. Existing smoke may already cover role gating. |
| Paid unshipped order, before submit | N/A | N/A | Shipping action is available; opening the ship UI/form does not call the ship API. |
| Paid unshipped order, success | 200 | `ADMIN_FULFILLMENT_SHIPPED` or current success code | Sends exactly one `POST /api/admin/fulfillments/{orderId}/ship` with ops bearer token, non-empty `requestId`, and trimmed `carrier`/`trackingNo`; detail and active list row update to shipped; form/dialog closes or exits pending state. |
| Duplicate submit while pending | Deferred 200 | N/A | Repeated clicks while the request is pending send exactly one ship request; submit control is disabled or visibly pending. |
| Created order | N/A | N/A | Shipping action is disabled/unavailable; no ship API call is sent. |
| Already shipped order | N/A | N/A | Shipping action is disabled/unavailable; no ship API call is sent. |
| Completed order | N/A | N/A | Shipping action is disabled/unavailable; no ship API call is sent. |
| Cancelled order | N/A | N/A | Shipping action is disabled/unavailable; no ship API call is sent. |
| Unknown/raw status order | N/A | N/A | Shipping action is disabled/unavailable; raw status remains visible; no ship API call is sent. |
| Backend status rejection | 409 | `ORDER_STATUS_INVALID` | UI shows backend `message`, `code`, and `traceId`; current detail/list snapshot is preserved; retry remains possible if current UX supports it. |
| Downstream timeout | 503 | `DOWNSTREAM_TIMEOUT` | UI shows backend `message`, `code`, and `traceId`; current detail/list snapshot and order status are preserved. |
| Generic fulfillment failure | 500 or current error status | Current fulfillment failure code | UI shows backend `message`, `code`, and `traceId`; no optimistic shipped state remains after failure. |

## Good / Base / Bad Cases

Good:

- Paid unshipped order exposes the ship action and requires explicit form submission before any API call.
- The ship request uses `Authorization: Bearer mock-ops-jwt-token`.
- The ship request body contains a non-empty `requestId`.
- The ship request body trims `carrier` and `trackingNo`.
- Duplicate submit while pending produces one API call.
- Success updates selected detail and current list row to shipped.
- Success does not copy any payment refresh/status field into the order main status.
- `ORDER_STATUS_INVALID`, `DOWNSTREAM_TIMEOUT`, and fulfillment-failure envelopes render `code`, `message`, and `traceId` and preserve the current snapshot.

Base:

- The smoke suite remains hermetic using Playwright route mocks for `/api/**`.
- Existing lower-level unit tests remain responsible for pure helper behavior; browser smoke focuses on UI/network integration behavior.
- The implementation should prefer extending the current admin order/payment smoke fixture and route state to preserve the new mock patterns from status, payment refresh, and cancel coverage.

Bad:

- Ship API is called before the user submits/confirms the ship form.
- Created, shipped, completed, cancelled, or unknown-status orders can send a ship request.
- Duplicate pending clicks send multiple requests.
- Whitespace carrier/tracking values are sent untrimmed.
- Error rendering drops backend `code`, `message`, or `traceId`.
- Failure mutates the selected order/list row to shipped.
- Success writes payment status into the order main lifecycle status.
- The smoke relies on live backend, DB, Redis, MQ, Nacos, Docker, or external logistics services.

## Required Tests And Assertion Points

Focused smoke command:

```powershell
cd frontend
cmd /c npx playwright test e2e/admin-order-payment-smoke.spec.ts --project=chromium
```

Required assertion points:

- Paid unshipped order ship action is visible/enabled.
- Opening the ship UI/form does not call `POST /api/admin/fulfillments/{orderId}/ship`.
- Submit sends `POST /api/admin/fulfillments/{orderId}/ship`.
- Request includes `Authorization: Bearer mock-ops-jwt-token`.
- Request JSON includes non-empty `requestId`.
- Request JSON includes trimmed `carrier` and trimmed `trackingNo`.
- Duplicate submit while pending sends one request.
- Created, shipped, completed, cancelled, and unknown orders cannot send a ship request.
- `ORDER_STATUS_INVALID` failure displays backend `message`, `code`, and `traceId`.
- `DOWNSTREAM_TIMEOUT` or fulfillment failure displays backend `message`, `code`, and `traceId`.
- Failure preserves selected detail and list row status.
- Success updates selected detail and active list row to shipped.
- Success does not replace the order lifecycle status with payment status.
